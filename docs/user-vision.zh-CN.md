## 我的核心判断

以后引擎开发会越来越多地由 Agent 参与。所谓 AI-native，不应该只是在编辑器里增加聊天框、接入 MCP，或者让 AI 能够创建实体。我们真正需要考虑的是：怎样让 Agent 理解、修改、编译、运行和调试一个足够复杂的引擎，并且能够验证自己所做的工作。

我希望这个项目重点研究社区里还没有被充分解决的问题，而不是简单复制现有开源引擎的功能集合。

## Git 与 SVN 友好是基础要求

真正对 AI 和团队开发友好的引擎，首先必须对 Git、SVN 等版本控制系统友好。

这意味着我们需要持续关注：

- 场景、资产描述、配置和项目设置是否尽可能采用可读、可比较的格式。
- 序列化结果是否稳定，避免无意义的顺序变化和格式变化污染 Diff。
- 实体、组件和资产是否具有稳定身份，而不是依赖数组位置或临时运行时编号。
- 一次修改能否形成范围清楚的小型变更，方便人类和 Agent 审查。
- 多人或多个 Agent 同时修改时，冲突是否容易理解、合并和回滚。
- 格式升级是否有明确版本、迁移工具和可验证结果。
- 生成文件、缓存和 Cook 产物是否与权威源文件严格分离。

Git/SVN 友好不能只理解为“文件可以提交”。它应当成为场景格式、资产管线、编辑器事务和 Agent 操作方式的共同约束。

## 必须认真研究的复杂性

引擎仍然是一个足够复杂的软件系统。我们不能因为 Agent 可以生成代码，就跳过下面这些基础选择。

### 语言与底层实现

需要研究引擎核心采用什么语言，以及这种选择对以下方面的影响：

- 运行时性能、内存控制和硬件 API 接入能力。
- 编译速度、增量构建和链接时间。
- 跨平台工具链与依赖管理。
- 调试器、Profiler、静态分析和 Sanitizer 支持。
- Agent 阅读代码、理解所有权和安全修改代码的难度。
- ABI 稳定性、插件边界和未来脚本层的接入成本。

这里不预先假定“越底层越好”或者“语言越新越好”。最终选择必须用真实工程指标验证。

### 编译与迭代速度

编译性能本身应该成为引擎的重点能力，而不是开发后期才处理的问题。

需要考虑：

- 如何减少头文件传播、模板膨胀和不必要的模块耦合。
- 如何建立可靠的增量编译、并行编译、缓存和分布式编译路径。
- 如何让脚本或数据修改不必触发整个 C++ 引擎重新构建。
- 如何记录每次构建中最慢的编译单元、模板实例化、代码生成和链接阶段。
- 如何让 Agent 获得结构化的编译诊断，而不是只能阅读一大段终端文本。
- 如何由工具自动判断某次改动为什么扩大了重编译范围。

目标不只是“最后能编译通过”，而是让人类和 Agent 都能理解编译时间花在了哪里，以及怎样缩短反馈周期。

### 面向开发者的脚本层

引擎核心语言和开发者使用的脚本语言不一定相同。脚本层需要同时服务快速迭代、人类开发者和 Agent。

需要研究：

- 脚本层使用已有语言、嵌入式语言，还是受约束的领域语言。
- 是否支持热重载，以及热重载时如何保存和迁移运行状态。
- 类型、组件和引擎 API 能否从同一份 Schema 或反射信息生成。
- 脚本错误能否关联实体、场景、资源、调用栈和对应源码。
- Agent 能否在修改前检查 API、类型约束和影响范围。
- 脚本性能是否可分析，热点是否可以平滑地下沉到原生模块。
- 脚本、原生插件和场景数据之间的版本兼容如何管理。

脚本层不能只是为了“写起来方便”。它还应该降低修改成本、缩短验证循环，并提供清晰的失败边界。

## AI-native 应该怎样与 Agent 结合

Agent 需要的不只是执行命令的接口，而是一套完整的工程反馈闭环：

1. 理解：获得模块边界、类型、依赖、线程模型、硬件约束和相关测试。
2. 修改：通过范围明确、可校验、可撤销的操作修改代码、场景和配置。
3. 构建：使用统一命令编译，并得到结构化的耗时、缓存命中和失败原因。
4. 运行：能够 Headless 运行、控制帧数、固定随机种子并复现输入。
5. 观察：读取 World、日志、内存、线程、CPU、GPU 和资产管线状态。
6. 调试：把异常现象追溯到实体、组件、系统、Shader、资源、命令提交和具体代码版本。
7. 验证：运行测试、比较状态、检查截图和性能预算，证明修改有效且没有引入回归。

MCP、CLI、JSON-RPC 或编辑器只是这些能力的入口。真正的价值来自引擎内部是否存在一致、可查询、可验证的数据和调试模型。

## 希望形成的项目特色：Agent 友好的底层调试

我尤其重视如何让 AI 对引擎的硬件层和底层系统进行有效调试。这可能是本项目最值得形成差异化的方向。

重点包括：

- 把 CPU 帧、线程调度、任务依赖、锁等待、内存分配和缓存行为暴露为结构化数据。
- 记录 GPU Adapter、驱动、Feature、资源状态、Pipeline、Pass、Barrier、Command Buffer 和时间戳。
- 把 Shader 编译错误、GPU Validation、设备丢失和渲染异常关联到 Shader、材质、Pass、实体及源码版本。
- 允许 Agent 查询“这一帧为什么变慢”“这个资源为什么发生错误状态转换”“这次修改为什么增加了 GPU 等待”。
- 对两次运行进行 CPU/GPU、内存、编译耗时和 World 状态的可重复比较。
- 在不同硬件和驱动上保存可移植的诊断包，让 Agent 即使不能直接操作对应机器，也能分析问题。
- 为底层操作设置能力边界，避免 Agent 获得无约束的内存、进程或系统访问权限。

这里的目标不是让 Agent 取代 RenderDoc、PIX、Nsight、Tracy 或系统调试器，而是让引擎能够采集、关联和解释这些工具产生的信息，形成 Agent 可以使用的诊断上下文。

## 用来约束后续设计的问题

每次增加核心功能时，都应重新检查：

- 它的权威数据能否被 Git/SVN 清楚地比较和合并？
- 修改它是否会触发不必要的大范围重新编译？
- 人类和 Agent 是否使用同一套公开能力，而不是 AI 专用后门？
- Agent 能否在不读取整个仓库的情况下理解相关模块？
- 失败结果是否结构化、可定位、可复现？
- 性能变化能否归因到具体代码、系统、资源和硬件阶段？
- Agent 能否拿出测试、Trace、Diff 或性能数据证明修改正确？
- 这项能力是否真的解决了现有社区方案没有解决的问题？

如果这些问题长期得不到回答，即使引擎接入了很多 AI 工具，也不能称为真正的 AI-native。

## 新增愿景：让 Agent 理解人类正在看的界面与场景

引擎编辑器不能只向 Agent 提供截图。截图适合判断颜色、构图和材质观感，却不擅长准确表达控件、实体、数据绑定、遮挡、渲染阶段和源码来源。

我希望在一个窗口运行引擎、另一个窗口使用 Agent 时，可以直接描述“刚选中的角色”“右上角面板”“这个粒子太亮”或“这里运行时卡顿”。Agent 应结合当前焦点、选区、光标、视口可见实体、局部图像和渲染证据理解目标，而不要求用户手工查找对象名称或反复截图。

这要求编辑器 UI、场景对象、VFX、材质、Render Pass、资源和源码共享稳定身份，并提供低开销、实时增量的语义观察。人类、Agent、自动化测试和可访问性工具应使用同一份公开能力。

## 新增验证方向：VFX 与 Hybrid Pixel 游戏

粒子和特效系统既要让 Agent 全面编辑，也要保持极高运行时效率。Agent 修改应落到可比较、可约束的 VFX 图和参数，并能看到模拟、排序、透明覆盖、显存、Shader 编译和渲染成本，而不是只判断截图是否好看。

项目将使用 Hybrid Pixel 2.5D 游戏验证引擎。它需要像素角色、3D 场景、灯光、阴影、深度、雾、后处理和粒子协同工作，能够同时暴露资产管线、透明渲染、脚本迭代和语义观察中的真实问题。HD-2D 是参考风格，不应被当成一个现成算法或引擎唯一用途。

大量二维角色不能依赖 AI 为每个人独立生成所有方向和动作的完整序列帧。希望引擎提供类似二维骨骼但更适合像素画的模块化系统：角色共享骨架和动作，头发、服装、武器和身体部件可以替换，复杂手脚、表情和夸张攻击仍允许局部逐帧修正。编辑时保持结构化 Puppet，发布时默认烘焙成低成本 Sprite；Agent 能理解并修改具体骨骼、部件、方向、动作阶段和某个失败帧。
